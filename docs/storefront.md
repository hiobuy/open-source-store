# Storefront & Member Center (Web Worker)

The repository root is a Next.js 16 application (formerly the standalone `client/` storefront), run by vinext / Vite and deployed as the Cloudflare Worker `hiobuy-procurement-website`. Together with the Hono API Worker in `server/`, it forms a two-Worker, single-domain topology; see [Deploy and environment](getting-started/deploy.md) for deployment and routing. This page documents storefront configuration and conventions; the admin console frontend lives in `src/admin/` (see [Local development](development.md)).

Tech stack: Next.js 16, TypeScript, Tailwind CSS v4, shadcn/ui (`default` style), Zustand, and next-intl. Pages use explicit JSX with no runtime template engine or component registry. `/admin` is rendered client-side only via `src/app/admin/[[...path]]/page.tsx` mounting `src/admin/AdminRoot.tsx` and is outside the scope of this page.

## Environment and Commands

Requires Node.js 22.12+ and npm. Run `npm ci` first.

| Command | Purpose |
| --- | --- |
| `npm run dev` | Starts the vinext dev server (Web Worker) |
| `npm run dev:api` | Starts the API Worker (`127.0.0.1:8787`) |
| `npm run lint` | ESLint (ignores `server`, `src/admin`, `src/domain`, `src/mocks`, shared `src/types` files, `drizzle`, `scripts`, and `docs`) |
| `npm run typecheck` | Generates Worker / vinext route types and runs all `tsc -p` checks |
| `npm run format` / `npm run format:check` | Prettier format / check |
| `npm test` | Vitest |
| `npm run build` | `build:web` (builds the Web Worker) plus `build:api` (API Worker dry-run bundle to `dist-api/`) |
| `npm start` | Locally previews the built Web Worker |
| `npm run cf-typegen:web` | Generates Cloudflare binding types for the Web Worker |
| `npm run deploy:web` | Deploys the Web Worker |

`typecheck` depends on route types generated by `vinext typegen` (such as `LayoutProps`); do not run bare `tsc` alone.

Storefront pages load business data from the API, so local development requires running both `npm run dev:api` (with `.dev.vars` in place) and `npm run dev`. In development, `apiDevProxy` in `vite.config.ts` forwards all `/api/*` and `/agents*` HTTP requests to `127.0.0.1:8787`; WebSocket upgrades are not proxied in development.

TypeScript is pinned to 5.9 (`typescript-eslint` requires `<6.1`); `next-intl` is pinned to exact version `4.14.9` because `4.15.3` breaks `vinext dev` with `getRequestConfig is not a function`. Verify before upgrading either package.

## Business APIs

All business data comes from same-origin `/api/*` (the same API Worker used by the admin console), with no storefront proxy in between:

- Storefront browser code requests `/api/...` directly, and Better Auth sets its cookies directly on the current domain, so in local development the storefront and admin console share the same API, database, and session. Same-origin enforcement for write requests is handled by the API's `clientCors` middleware (`server/client-api/access.ts`) and Better Auth's `trustedOrigins`.
- Product detail SSR (`src/lib/server/product.ts`) calls the API via `fetchApi` in `src/lib/server/api.ts`, forwarding only Better Auth cookies. In production, it uses the `API` service binding defined in `cloudflare.config.ts` (Worker `hiobuy-procurement`; deploy the API Worker first) with the incoming request's public origin so Better Auth sees the same host and cookie names as the browser. In development, it uses `API_INTERNAL_ORIGIN` from `.env` (e.g., `http://127.0.0.1:8787`; HTTP is allowed only for `localhost` / `127.0.0.1`); when set, it takes precedence over the service binding and is written into Worker config only in non-production builds. Local `vinext dev` cannot resolve service bindings, so if `API_INTERNAL_ORIGIN` is unset, product-page API calls fail and the page falls back to its standard error state.
- Auth return URLs are passed as relative paths by the storefront client: `/login?verified=1` for registration and resending verification emails, the page's `redirect` target for Google sign-in, and `/login?social_error=google&redirect=...` on failure.
- In storefront auth responses, `postAuth` (`src/lib/procurement/client.ts`) replaces Better Auth's returned `token` with a `sessionEstablished` flag and discards the token; session persistence relies solely on cookies.

The browser API client lives in `src/lib/procurement/client.ts`. `src/lib/client/services/*-types.ts` retains only legacy data structure types still referenced by page components and contains no request code.

The purchase order detail inquiry modal (`src/components/consult-detail.tsx`) preserves its UI but is not yet wired to an inquiry API: it can be enabled by passing `loadConsult` / `sendMessage` implementations, and its entry point is currently hidden via `SHOW_ITEM_CONTACT`.

Notification `href` values (such as `/app/packages/:id`) are API-provided data and remain unchanged; the storefront maps them to `/member-center/...` routes in `src/components/features/logistics/procurement-notifications.tsx`.

### Authentication Requirements

Sign-in, registration, password recovery, and email confirmation use the procurement API's Better Auth email and Google flows.

- Because the storefront and API share an origin, Better Auth `trustedOrigins` includes the current origin by default; verification email return URLs use `/login?verified=1` passed by the storefront client.
- Turnstile site keys must include the storefront domain.
- Google sign-in is controlled by the upstream `security/public` toggle; the storefront and admin console share one callback, so register only `<origin>/api/auth/callback/google` in the Google OAuth console.

## Fixed Theme and Local Content

- Theme is not fetched at runtime: `src/config/site.ts` fixes the store identifier and supported language list, the logo lives at `public/assets/brand/hiobuy-logo.png`, and CSS fixes the primary color (`hsl(3 98% 41%)`), Poppins font, and border radii.
- Blog posts (`src/content/blog/`) and help center articles and categories (`src/content/help-center/`) are local JSON files with no runtime content API calls; help articles belong to categories via `category_id`.

## Directory Structure

- `src/app/(site)/(storefront)/`: Shop and member pages; shared Header / Footer live in the group layout.
- `src/app/(site)/(storefront)/(with-sidebar)/`: Member pages with the member sidebar mounted by this group's `layout.tsx` (route group names do not appear in URLs). Place new sidebar member pages here and render only page content; place detail, creation, and payment pages under `(storefront)/member-center/` without the sidebar.
- `src/app/(site)/(auth)/`: Login, registration, forgot password, reset password, and email confirmation.
- `src/components/layout/`: Header, Footer, mobile nav, member sidebar, and shared layout containers.
- `src/components/features/`: Cross-page business modules. Single-page components go in that route's `components/` directory, with dedicated logic and hooks in `lib/` and `hooks/`.
- `src/components/ui/`: shadcn primitives and shared interactive components.
- `src/lib/procurement/`: Browser client, session helpers, and types for the procurement API.
- `src/lib/server/`: Server-side API calls (`api.ts`), product preloading, and local blog/help content loaders.
- `messages/*.json`: Flat translations for all 12 languages.
- `public/assets/`: Static assets.

`page.tsx` files are Server Components responsible for metadata, data loading, and static content; interactive routes keep a sibling `page-client.tsx`.

Naming conventions: `PascalCase` for React components, `kebab-case` for source files and route directories, `useCamelCase` for hooks in `use-kebab-case.ts` files. Keep Next.js convention filenames intact. Legacy URLs are handled via 308 redirects in `next.config.ts`.

## Internationalization

Defaults to English (`en`) and supports `cn`, `ja`, `ko`, `es`, `fr`, `de`, `pt`, `ru`, `pl`, `ar`, and `it`, with no `[locale]` URL prefix.

- The selected language is stored in a 1-year `locale` cookie. The browser uses a shared Zustand store while the server uses a per-request store; client components read the current locale via `useLocaleStore` and refresh the server page when switching languages.
- Upstream API locale codes, HTML `lang`, and text direction are mapped centrally in `src/lib/locale.ts`; `zh` / `zh-CN` map to `cn`, and `pt-BR` maps to `pt`. Arabic is RTL.
- Translations use namespace-free `useTranslations()` / `getTranslations()` with English source text as keys containing no literal `.`. Any new copy must be synced across all 12 locale files. Messages with custom business placeholders use `t.raw()` and are substituted by the component.

## SVG and Cloudflare

SVGs are processed by `vite-plugin-svgr`—for example, `import { default as ServiceIcon } from "@/assets/home/s1.svg"`—and recolored via classes such as `text-primary`. Because vinext transforms shorthand default image imports into image metadata objects, SVG components must use the aliased default export syntax above.

`cloudflare.config.ts` configures the Worker (`ASSETS` binding and the `API` service binding pointing to the API Worker), and `vite.config.ts` registers vinext, SVGR, and the Cloudflare Vite plugin. Currently there is no caching, image optimization, or KV / D1 / R2 binding on the Web Worker. Configure your Cloudflare account authentication before deploying.

Keep secrets strictly in local environment files or Cloudflare secrets; never commit them.
